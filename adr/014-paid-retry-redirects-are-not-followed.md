# ADR-014 — A paid retry does not follow redirects in v0.1

**Status:** Accepted · **narrows `SPEC.md` §6.1 for v0.1; revisit at v0.2**
**Amended S15b** — see "Amendment (S15b)" below, which closes O52.

Closes PLAN.md open item **O26**.

## Context

SPEC §6.1 says:

> Automatic redirect following is disabled for a paid retry **unless redirect target has the
> same normalized origin**. Cross-origin redirect raises `PaidRedirectBlockedError`.

Read literally, that permits following a **same-origin** redirect on a paid retry. Both SDKs
today follow neither: every 3xx on the request that carries `PAYMENT-SIGNATURE` ends the call.
Cross-origin raises `PaidRedirectBlockedError`, as required. Same-origin is classified by
`classify_paid_attempt` / `classifyPaidAttempt` as **ambiguous**, with
`causeCategory: "redirect-not-followed"`, and the reservation is **retained** to its TTL.

That money classification is already correct, and it was the S8 fix that made it so. Before
S8 a same-origin 3xx fell into the `!response.ok` branch and was treated as a definitive
refusal — reservation released, `paid: false`. A 3xx is not a refusal. The merchant may well
have settled and be redirecting to the delivered resource, and releasing there hands back
budget for money that moved. Three frozen `completion.paid-attempt` vectors now put a 403, an
unsuccessful settlement, and a 307 side by side so the three cannot be collapsed back into one
non-2xx branch.

What is left open is the **behaviour**, not the accounting: the call fails where SPEC §6.1
allows it to succeed. This ADR decides that.

## Decision

**v0.1 does not follow any redirect on a paid retry, including a same-origin one.** A
same-origin 3xx remains an `AmbiguousPaymentError` with `causeCategory:
"redirect-not-followed"` and a retained reservation. The CLI reports it under exit code **8**,
alongside every other ambiguous outcome, with the same "do not retry without checking the
merchant" line on stderr.

Following a same-origin redirect is deferred to **v0.2**, where it gets its own design, its own
threat model, and its own tests. The "Design sketch" section below is what that work starts
from, so the deferral does not throw away the analysis.

## Rationale

### Following means re-transmitting one authorization to a second URL

This is the substance of the decision, and it is not a small thing. The
`PAYMENT-SIGNATURE` header carries a single authorization for a single request. To follow a
redirect, tx402 must either re-send that same header to the new URL, or plan and sign again.

- **Re-sending the same header is a new replay surface.** One authorization would exist at two
  endpoints. Same-origin means the same host, which is not the same as the same trust boundary:
  a path on a shared host can be operated by a different tenant, and an open redirect on the
  merchant's own origin is a common enough web vulnerability that "same origin" cannot be
  treated as "same party". The buyer SDK has no way to tell the two apart from the outside.
- **Signing again is a second payment.** Every attempt re-plans and re-signs with a fresh nonce
  by design, so a "follow" implemented as a re-sign is indistinguishable from paying twice for
  one resource. It would need its own budget reservation, and the caller would be charged twice
  for a redirect they never asked about.

Neither branch is a small change, and picking the wrong one costs real money rather than a
failed request.

### The rules a correct implementation needs are not free either

RFC 9110 §15.4 gives different method-and-body rewrite rules per status: 301/302/303 may
rewrite a non-GET to GET and drop the body, while 307/308 must preserve both. tx402's replayable
body machinery (`bodyFactory`, `_fresh_body`) exists precisely because a body can only be
transmitted once, so a follow has to decide whether the second transmission gets the same bytes,
regenerated bytes, or no bytes — and the answer differs by status code. A hop bound is needed on
top, or a redirect loop becomes an unbounded sequence of requests each carrying an
authorization.

### SEC-005's wording points the same way, and does not contradict this

SEC-005's acceptance criterion reads "Cross-origin 301/302/307/308 tests fail **before
transmitting** `PAYMENT-SIGNATURE`", which is written as though the block guards a _second_
transmission — the redirect follow. That reading supports the eventual feature, and it is the
strongest argument on the other side. It is recorded here rather than dismissed. But it argues
that following should be _possible_, not that v0.1 must ship it, and the current behaviour
satisfies the acceptance criterion trivially: nothing is ever transmitted twice.

### Not following is the conservative failure, and it is honest

The failure mode of not following is a call that returns `AmbiguousPaymentError` when it could
have returned the resource. The caller is told the exact truth — the merchant redirected, tx402
did not follow, and the payment may or may not have settled — the budget is held rather than
handed back, and no authorization exists anywhere twice. The failure mode of following it
wrongly is a signature at an endpoint the buyer never chose. Between an unnecessary failure and
an unintended transmission of an authorization, v0.1 takes the failure.

### It is observable, so nobody has to guess

`causeCategory: "redirect-not-followed"` is distinct from every other ambiguous cause, appears
in the SPEC §10 diagnostics, and is documented in the error reference. A merchant whose flow
depends on a post-payment redirect can be identified from the buyer's logs without reading tx402's
source.

## Amendment (S15b) — the cross-origin error the SPEC names is now the one raised

Closes PLAN.md open item **O52**, filed by the S15 pre-publication audit.

This ADR said "cross-origin raises `PaidRedirectBlockedError`, as required", and "T-012 is
unaffected. It asserts the cross-origin block, which is unchanged." Both statements were
true of `issuePaidRetry`, which does create that error — and false of the client a caller
actually uses. `attemptPayment` caught it and replaced it with `AmbiguousPaymentError`
carrying `causeCategory: "redirect-blocked"`; Python mirrored the same substitution. The
class SPEC §6.1, the error taxonomy, the error reference, and this ADR all promise was
therefore unreachable from `client.fetch`, and the frozen vector and both integration tests
asserted the substitute — cross-language parity on the wrong public error.

**What changes:** the error identity, and nothing else.

- A cross-origin redirect on a paid retry raises **`PaidRedirectBlockedError`**
  (`TX402_REDIRECT_BLOCKED`, `retryability: "no"`, so `retryable` is `false`), carrying the
  `fromOrigin` / `toOrigin` SPEC §8 requires of that code, plus
  `reservationExpiresAtEpochMs` and `causeCategory: "redirect-blocked"`.
- `context.paid` stays `"unknown"` and the **reservation stays retained to its TTL**. That
  disposition was always right and is untouched: SEC-005 stopped the follow-up, not the
  original transmission, so the merchant has the signature and may have settled.
- The disposition table now carries `kind` and `errorCode` as separate fields (ADR-016), so
  a disposition can keep its money semantics while naming a different public error.
- **The CLI exit code moves from 9 to 8.** This ADR always described it as 8 — "the CLI
  reports it under exit code 8, alongside every other ambiguous outcome" — while
  `EXIT_CODE_BY_ERROR` mapped it to 9 in both languages. 8 is the "money may have moved, do
  not retry blindly" code, and this error is reachable only after transmission, so 8 is
  what the sentence above always meant. Exit 8 is now shared by exactly the two codes that
  can only arise post-transmission.

**A same-origin 3xx is unaffected**, in every respect: still not followed, still
`AmbiguousPaymentError` with `causeCategory: "redirect-not-followed"`, still retained. The
v0.2 design sketch below stands unchanged.

**The frozen vector `completion.paid-attempt.ambiguous-after-transmission` changes** — its
redirect row gains `errorCode: TX402_REDIRECT_BLOCKED` — which is why this is an amendment
to an accepted ADR rather than a bug fix. The 3xx vectors this ADR was written to protect
are not touched.

## Consequences

- **No code changes** _as originally accepted at S12_. The S15b amendment above changes the
  error class, the vector's `errorCode`, and one exit-code row. This ADR otherwise records a
  decision the implementation already embodies. It exists so that a future reader finds a
  decision rather than an omission, and so the SPEC §6.1 divergence is declared rather than
  silent.
- **SPEC §6.1's same-origin clause is narrowed for v0.1.** tx402 implements the MUST NOT half
  (cross-origin is blocked) and declines the permitted half (same-origin is not followed).
  Nothing in SPEC requires the follow, so this narrows a permission, not a requirement.
- **The CLI has no `--follow-redirects` flag**, and should not grow one as a workaround. A flag
  would move the decision to a caller who has strictly less information about the merchant's
  trust boundary than tx402 does, and it would do so at the exact moment money may already have
  moved.
- **T-012 asserts the cross-origin block, which is unchanged in substance.** Its expected
  error class changed at S15b — see the amendment above.
- **The 3xx frozen vectors are unaffected.** The `completion.paid-attempt` vectors covering
  a same-origin 3xx already encode this behaviour; the decision is to keep them, not to
  change them. The cross-origin row of `ambiguous-after-transmission` changed at S15b.

## Design sketch for v0.2

Recorded so the deferral is a schedule decision rather than a loss of analysis. A v0.2
implementation would need all of:

1. **Same-origin re-transmission only**, with origin compared on the normalized form already
   used by `PaidRedirectBlockedError`, and the authorization re-sent rather than re-signed —
   one payment, one signature, as SPEC §6.7 requires.
2. **A hop bound of 1.** More than one hop multiplies the number of endpoints that have seen the
   authorization for no observed merchant need. Exhausting it is ambiguous, not a refusal.
3. **Per-status method and body rules** from RFC 9110 §15.4, with 303 forcing GET and dropping
   the body, and 307/308 requiring a replayable body — a `bodyFactory` absent here is a
   `NonReplayableRequestError`, decided before the first transmission rather than after.
4. **Opt-in, off by default**, so an existing caller's behaviour cannot change under them in a
   minor release.
5. **New conformance vectors** covering the hop bound, each status's rewrite rule, and the
   interaction with `maxPaidAttempts` — landing in both languages together per O29.
6. **A threat-model note on open redirects**, since the whole safety argument rests on
   same-origin implying same party, which it does not always.
