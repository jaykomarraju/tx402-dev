# ADR-024 — The two CLIs emit one `--json` document; Python resolves to the TypeScript shape

**Status:** Accepted · **changes no MUST; changes the Python CLI's `error.context` and one error's `details`/`message`**

Filed at S35, remediating O107. `docs/.../guides/cli.mdx` opens: _"Both packages install the
same `tx402` command with the same flags, the same `--json` document, and the same exit
codes."_ S34 drove both CLIs across all seventeen test-merchant scenarios and found the
sentence false in the `--json` document, though true in flags and exit codes.

## Context

Measured this session, both CLIs, identical arguments, field-by-field diff (the run is pinned
by `core-spec/cli-json/expected.json` and the two tests that read it):

- **Exit codes are identical** in all 17 scenarios: `0,0,9,0,9,5,0,8,9,8,9,9,9,8,8,8,0`.
- **Two divergences, both inside `error`, on the post-routing failures:**
  1. On every one of the eleven scenarios that fail after a route is planned, the Python
     `error.context` carried only `requestId`/`phase`/`paid`(/`reservationId`), while
     TypeScript also carried `network`, `scheme`, `amountAtomic`, and `assetId`. So
     `jq -r '.error.context.network'` returned a value from the npm CLI and `null` from the
     PyPI one.
  2. `rechallenge-malformed` diverged further: TypeScript's `details` was
     `{reason, schemaPath, status}` and its `message` "Merchant re-challenged undecodably";
     Python's `details` was `{status, reason, attempt, maxPaidAttempts, decodeReason,
schemaPath}` and its `message` the longer "Merchant re-challenged after the signature
     with a PAYMENT-REQUIRED that does not decode". Python's context here also omitted
     `reservationId`, which it carried everywhere else.

SPEC does not decide this. `Tx402ErrorContext` (SPEC §8) declares `network?`, `scheme?`,
`amountAtomic?`, `assetId?`, `paid?`, `reservationId?` — **all optional** — and the per-code
"required context" column is satisfied in both languages (S34 confirmed every required key).
Both repairs are SPEC-legal; neither language violates a MUST. This is a judgment call about
what the shared document _is_, not about what the specification compels.

## Decision

**The `--json` document is one cross-language contract, and where the two implementations
disagree, Python resolves to the TypeScript shape.** TypeScript is the reference from which
behavioural prose and the frozen conformance vectors are written (ADR-023); resolving parity
toward it gives one rule — "Python emits what TypeScript emits" — rather than a per-field
negotiation, and keeps the whole fix in one file (`packages/tx402-python/src/tx402/client.py`),
leaving the reference implementation and the 73 vectors untouched.

Concretely:

1. **Route context (divergence 1).** A single helper, `_route_context(selection, …)`, builds
   the post-routing `Tx402ErrorContext` with `network`/`scheme`/`amountAtomic`/`assetId` from
   the selected route — the mirror of the one object TypeScript threads from `client.ts:928` —
   and every post-routing failure site now uses it. This only ever _adds_ diagnostic fields to
   the Python document; it removes nothing.

2. **`rechallenge-malformed` (divergence 2), decided explicitly and separately.** Python now
   mirrors `client.ts:1129` exactly: message "Merchant re-challenged undecodably", and
   `details = { ...decodeError.details, status, reason: "rechallenge-undecodable" }`, so the
   supplementary `attempt`, `maxPaidAttempts`, and `decodeReason` keys Python used to add are
   gone and `schemaPath` survives. Its context gains the route fields and `reservationId` like
   every other post-routing failure.

   This is the one place the decision _removes_ information from the shipped Python document
   rather than adding it. It is deliberate. TypeScript is the reference; a "same document"
   claim resolved toward the reference is worth more than three supplementary keys on one error
   path — and `decodeReason` was the only one of the three with real diagnostic value, which
   TypeScript itself discards by overwriting the decode error's `reason`. Preserving a decode
   reason on this path is a legitimate future improvement, but it belongs in **both** languages
   and the reference at once, not as a lingering divergence that documents itself.

## The guard, not the fix

The field population is the fix; the guard is the deliverable. `core-spec/cli-json/expected.json`
records the canonical document — the TypeScript CLI's normalized `--json` for all 17 scenarios,
generated by `tools/cli-parity`. `packages/tx402/test/cli-json-parity.test.ts` re-derives it
from the TypeScript **source** and pins it; `packages/tx402-python/tests/test_cli_json_parity.py`
pins the Python CLI to the same file. A change to `error.context` (or anything else in the
document) in **either** language now fails a test, and the two can only move together by
regenerating the golden. The normalization erases only what the SDK does not promise to
reproduce byte-for-byte — identifiers, durations, the latency-derived health score, the
merchant's body, and ephemeral redirect origins; everything the SDK produces is compared
verbatim.

## Consequences

- The Python CLI's `error.context` gains four fields on eleven failure paths, and
  `rechallenge-malformed` loses three supplementary `details` keys and changes one message
  string. No wire format, schema, or MUST changes; `Tx402ErrorContext` already declared and
  serialized every field.
- The already-published PyPI `tx402==0.0.0` is immutable and its CLI still emits the old
  shape. That is acceptable: `0.0.0` is a name-reservation placeholder, and the correction
  lands with the first real release.
- A future divergence in the CLI document is now a failing test in the language that drifted,
  not a finding a cold pass has to rediscover by hand.
